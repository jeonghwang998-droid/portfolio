Background

RAG의 개념은 알고 있었지만, 실제 AI 시스템을 구축하고 운영해본 경험은 없었습니다.

인턴으로 고객 상담 자동화가 필요한 기업의 채팅봇 구축 업무를 맡았습니다. 처음 접하는 Channel Talk으로 실제 업무에 쓰이는 AI 상담 시스템을 구현했습니다.

처음에는 코딩 없이 LLM·RAG 기반 상담을 구현할 수 있을지 의문이었습니다. 가이드를 참고해 Workflow와 Knowledge를 직접 구성하고 테스트하면서, 복잡한 AI·자동화 기능을 플랫폼이 쉽게 쓸 수 있도록 추상화해 제공한다는 점을 이해했습니다. 이를 통해 LLM과 RAG가 실제 서비스에서 어떻게 쓰이는지 알게 됐습니다.

내가 한 일
시간대 3구간 분기 설계, 메뉴·안내 멘트 설계
  • 트리거는 고객이 전화를 걸었을 때입니다.
  • 시간대를 비운영시간 / 점심시간 / 운영시간 3구간으로 나눴습니다.
  • 브랜치를 2단계로 중첩했습니다. 좁은 조건(점심시간)을 먼저, 넓은 조건(운영시간)을 나중에 검사합니다. 순서를 바꾸면 점심시간이 운영시간에 포함돼 걸러지지 않습니다.
  • 메뉴는 A/S 접수, 비용·기간, 설정·설치, 구입, 챗봇 링크, 상담사 연결, 다시듣기로 구성했습니다. 상담사 연결 시 안내·부재중 처리 멘트도 설계했습니다.

메뉴 개편안

검토 중인 제안입니다. 선택지가 많아 급한 고객이 불편하고 챗봇 도입 취지가 퇴색되므로, 챗봇 링크를 앞으로 올리고 상담 연결 메뉴를 통합하는 안입니다.

  • 대리점 데이터 3단계 비교·병합 — 원본 → 부분 목록 → 회사 최종본을 비교하고 병합했습니다. 부분 목록 기준 삭제분 중 일부가 최종본에 살아 있어 복원했고, 다중 번호 항목이 통째로 삭제될 뻔한 오류를 검증 과정에서 잡았습니다.

05

Technical Insight

01

LLM/RAG의 실제 적용

이론으로만 알던 RAG를 실제 기업 상담에 적용하며, AI 기술이 서비스에 연결되는 방식을 경험했습니다.

02

RAG Pipeline 이해

Document가 그대로 LLM에 전달되는 것이 아니라, Parsing, Chunking, Embedding, Indexing, Retrieval을 거쳐 관련 정보가 Context로 전달되는 구조를 이해했습니다.

03

Workflow 기반 서비스 구성

조건과 분기를 시각적으로 구성해 시나리오를 설계하고, 테스트를 거쳐 서비스에 맞게 수정했습니다.

04

서비스 관점의 개발 경험

요구사항 파악 → 설계 → 구현 → 테스트 → 문제 수정 → 재검증 → 운영의 흐름을 경험했습니다.

05

데이터 품질

RAG의 답변 품질은 지식 데이터의 구조와 정합성에 크게 좌우된다는 것을, 대리점·제품 데이터를 정제하며 확인했습니다.

02번은 일반적인 RAG 개념 기준이며, Channel Talk의 내부 구조를 확인한 것은 아닙니다.
